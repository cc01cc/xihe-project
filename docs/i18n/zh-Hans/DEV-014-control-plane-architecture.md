# DEV-014: CP 架构

> Control Plane（Java 25 + Spring Boot 4）是系统心脏：路由 + 认证 + MCP 反向代理 + 状态广播 + 会话管理 + 统一配置。约束：不做模块专属业务逻辑。与 DEV-016 以"CP 内部 vs 端到端工具路径"分界互引；端点以 `docs/api/openapi.yaml`/`docs/api/inventory.md` 为准，跨模块 ownership 和事件边界见根级 `spec/architecture/`、`spec/protocol/` 与 `spec/data/`；认证、授权、能力策略、审批和审计见根级 `spec/security/`（当前为 proposed）。

**本地架构校验（PLAN-0470 M2）**：CP 增加 test-scope ArchUnit 1.5.1，检查实际生产 Controller、应用组件及持久化类型的依赖，合成正反探针与生产检查分开。在 `packages/control-plane/` 执行 `mvn -o -q test "-Dtest=CpArchitectureTest"`，报告为 `target/cp-architecture/baseline.json`；探针入口为 `CpArchitectureRuleProbeTest`。初始严格规则仍因存量依赖失败，不表示当前源码已符合目标。逻辑归属图记录完整类型强连接分组，不把带上限的示例数当作总循环数，也不把 DTO/错误类型依赖环直接等同状态 writer 环。Compiler/Checkstyle 原用途与 error 级别不变。PMD 候选经实际局部试跑和依赖审计后未采用，未接入默认构建或生产 classpath。

## 1. 三通道

- **聊天通道**：`POST /api/v1/chat`（必填 `sessionId`/`branchId`/`content`，`202` + `runId`，指令发送）+ `GET /api/v1/events?sessionId=`（会话级持久 SSE，流接收）。CP 中转 UI↔Agent，流式分发到 UI。**注意**：CP 只转运聊天流量（租约/透传/审计），不组装 LLM 请求、不代理模型调用——模型调用由 Agent 直调 provider（见 DEV-013 §2.3）。
- **Follow-up Queue（PLAN-0442）**：`/api/v1/sessions/{sessionId}/follow-ups` 是 CP durable FIFO；每 Session 最多 5 条 outstanding。此版本要求部署保持**单个活跃 CP 实例**；多实例 CP 不在支持范围，因为 terminal handoff 使用进程内 after-commit wake，启动扫描只在实例启动时执行，不构成跨实例持久投递。入队/读取/撤回/继续不依赖浏览器 SSE；普通 Chat 在同一 Session admission 锁内要求队列为空。QueueItem 只在 CP 原子 admission child ChatRun 时物化为 Message，附件/branch 在 admission 时重验。终态事务先结算队列，dispatcher wake 等 `releaseRun` 释放本进程 single-flight 与 DB lease 后触发；启动扫描补偿本实例内丢失的 wake。多实例唤醒/恢复需独立设计与验收后才能启用。
- **Run Guidance（PLAN-0528）**：`/api/v1/chat/runs/{runId}/guidance`（`POST` 需 `Idempotency-Key` + `{content}`，`GET` 快照）承载运行中 Steering——Run-scoped、与 Message/Follow-up/EventStore 分离的 CP durable 记录（Flyway V77 `chat_run_guidance`）。作者由 TenantContext 派生；请求体不携带 `sourceKind`，服务端恒置 `user`（DB `CHECK source_kind='user'` fail-closed，guard 接入须新迁移 + Security 立项）。仅活跃 Run（`running|streaming|awaiting_approval`）接受提交（否则 `409 GUIDANCE_RUN_NOT_ACTIVE`）；同键幂等回放 `200`（仅 Run 属主；非属主 `403`，回放返回存储状态，终态不回转）。Run 终态事务内将未消费 pending 收敛为 `terminal_expired`（与 Follow-up settle 同位），不迁移到续跑新 Run。Agent 消费走服务间 `GET /internal/v1/chat/runs/{runId}/guidance/pending` + `POST .../{guidanceId}/consume`（consume 幂等；terminal-expired 后 consume 返回 `409 GUIDANCE_ALREADY_TERMINAL_EXPIRED`）。**无 Guidance 专属 SSE 事件**（裁定候选①）：UI 在提交后与 Run 终态事件时 refetch 快照。日志只记 id/sequence/status，不记正文。契约唯一冻结件：`spec/session/chat-run-operation.md` 的 `## Run Guidance`；跨层语义见 `plans/PLAN-0468-xh-chat-run-guidance/spec/target-contract.md`。延续 Follow-up 的**单个活跃 CP 实例**部署约束。**E2E-only 屏障（PLAN-0536）**：`/internal/v1/e2e/guidance-barrier/{runId}/{arm,release}` + `GET /{runId}` 仅以 `@Profile("e2e")` 注册（`dev`/`prod` 无该 profile，路由不存在；`/internal/v1/**` 已限定 `ROLE_INTERNAL_SERVICE`）。用途仅为确定「Guidance POST 已到 CP → 真实 cancel 成功 → release → 409」的时序；屏障挂在 controller 事务之外（service 事务内先锁 Session 再锁 Run，与 cancel 同序，停在那里会自死锁）。超时返回 `503 E2E_GUIDANCE_BARRIER_TIMEOUT` 且不落库。契约见 `plans/archive/PLAN-0536-xh-guidance-race-error-e2e/spec/e2e-guidance-barrier.md`。
- **MCP 反向代理通道**（`POST /api/v1/mcp`，另有同前缀 GET/DELETE）：JSON-RPC 解析 → 工具名提取 → 权限检查 → 请求改写 → 三层路由转发（详见 DEV-016）。CP 为纯 HTTP 反代，不依赖 MCP SDK。
- **状态分发通道**：Runtime/Workspace storage watcher → CP Workspace event ingress → UI Workspace SSE；ChatRun 仍独立使用 Session SSE，不把无 Session 文件事件塞入 Chat。

## 1a. 认证入口与单机本地模式（PLAN-0526）

- 认证入口为 `/api/v1/auth/**`（permitAll）：`register`/`login`/`refresh`/`me`。PLAN-0526 新增 `GET /bootstrap-status`（恒 200，`{initialized, localMode}`）、`POST /local-login`、`POST /local-password-reset`，并允许 register 在本地模式省略密码（服务端生成、201）。
- 单机本地模式由 `LocalModeService` 门禁：仅 `XIHE_LOCAL_MODE=true` + 回环来源 + `Origin`/`Host` 回环时可用，且签发对象必须是**唯一可登录用户（任意角色，含 ADMIN）**（否则 409）；本地模式跳过默认 admin seed，首用户获得实例级 `SUPER_ADMIN` **绑定**（PLAN-0610 起不再用 `ADMIN` 层级表述，见 `AuthController.java:58`）；其余一律 404 且不签发 token。门禁在应用层，`SecurityConfig` 不放开通配。
- PLAN-0558 登录防护：`/login` 按规范化账号 + 客户端 IP 双维度做固定窗口失败计数，达到阈值返回 429 `AUTH_RATE_LIMITED` + `Retry-After`；未知账号同计数并执行 dummy BCrypt；失败写 AUDIT JSONL，锁定/解锁写 `audit_logs`。计数为 CP 进程内有界表（单实例语义，重启清锁）；`X-Forwarded-For` 默认忽略，仅 `cp.auth.login.trusted-proxies` 命中的 `remoteAddr` 才解析；本地模式与 `/refresh` v1 不限流，`/register` 按 IP 限流且默认豁免回环。
- PLAN-0565 账号标识（裁定 #7）+ 决策 v29：`users.username` NOT NULL UNIQUE（V82 回填；字符规则与 agent 主体名/昵称共用 `NameFormat.PATTERN_SOURCE`＝英文字母（含大写）/ 中文汉字 / 数字，不得数字开头、不得含空格与符号，长度按列宽 ≤32）；注册可选自填（留空由 email 本地部分生成默认、冲突加序号，非法 400 `USERNAME_INVALID`/占用 409 `USERNAME_TAKEN`）；`LoginRequest` 字段由 `email` 改为 `identifier`——含 `@` 按 email 解析、否则按 username 解析，登录限流键与失败审计同步改口径（email 值仍 mask、username 公开可明文）。
- 契约见 [`spec/security/authentication.md`](../../../spec/security/authentication.md) §4/§5 与 `docs/api/inventory.md`。
- 新手首跑的完整链路（三条件 → onboarding → 建 Agent → 首条回复）与逐条可见判据见 [DEV-033](DEV-033-first-run-gold-path.md)。

## 1b. 实例所有权与 access token epoch（PLAN-0580）

- **实例 owner 是单例指针，不是第三种角色**：表 `instance_owner`（`id SMALLINT PK` + `CHECK (id = 1)`，行内 `owner_user_id` / `assigned_at` / `assigned_by`），指向的用户必须仍是 `users.role = 'ADMIN'`（不变式 I1）。所有权经 `PUT /api/v1/instance/owner` 转移：只有**当前 owner** 可发起（普通 ADMIN 仍 403 `NOT_INSTANCE_OWNER`），必须口令复核（401 `INVALID_CREDENTIALS`，复用 PLAN-0558 失败计数与 BCrypt 并发槽，不新增计数器），成功写 durable 审计 `instance_owner_transferred`；旧 owner 保持 ADMIN。
- **读面不泄漏账号标识**：`GET /api/v1/instance/owner` 任意已认证用户可读，返回 `{ownerUserId, assignedAt, isCurrentUser}`；无 ADMIN 时两个 owner 字段为 `null` 且 **200**（非 404）。响应刻意不含 `username`/`email`/`name` —— `/api/v1/users*` 是 ADMIN 面（PLAN-0581），在此暴露 owner 账号名等于给出账号枚举旁路。
- **守卫与写序**：`PATCH /api/v1/users/{userId}/role`（ADMIN-only）在单一事务内按固定顺序执行「实例锁 → 守卫 → `users.role` → default 集 resync（仅 `subject_type='user'`）→ `users.token_version + 1` → 审计」；锁序恒为 `instance_owner` 单例行 → 目标 `users` 行，首语句 `dbLockTimeout.apply()`（锁超时 → 503 `OPERATION_LOCK_TIMEOUT`，与 409 状态冲突严格区分）。守卫优先级：owner 保护（409 `INSTANCE_OWNER_PROTECTED`，审计 `user_role_change_denied` 用独立事务落库）先于 last-admin（409 `LAST_ADMIN`）；角色未变的请求是 200 空操作，不 bump 也不写审计。
- **access token epoch（`tv`）**：access token 除签名外还携带 `tv`（签发时的 `users.token_version`），唯一生产签发点 `AuthService.issueTokens`。每个请求由 `config/AccessTokenAuthenticator` 做一次按主键的用户行读取并比对，**三态 fail-closed**（`sub` 非 UUID / 用户行不存在 / `tv` 缺失或不匹配）一律按未认证处理 → 401 `AUTHORIZATION_REQUIRED`，**不得**变成 500；`JwtAuthenticationFilter` 与 `TenantContextInterceptor` 共用这一判定，撤销后的 token 既不建立 `Authentication` 也不写租户上下文。`InternalTokenFilter` 的 `cp.agent-api-token` 不是用户 access token，仍不写用户租户语义。详见 [`spec/security/authorization.md`](../../../spec/security/authorization.md) §4/§4.1。

## 1c. 用户管理面与双通道撤销（PLAN-0581）

- **用户管理面 6 条 route**（`controller/UserAdminController`，全部 `@PreAuthorize("hasRole('ADMIN')")`，与 0580 的 `UserRoleController` 共用 `/api/v1/users` 基路径但子路径不相交）：`GET /api/v1/users`（`q`/`role`/`status`/`includeDeleted`/分页，`size ≤ 100`，`createdAt` 倒序）、`GET /api/v1/users/{userId}`、`POST /api/v1/users`（closed 模式唯一建号出口，未给密码时一次性返回 `temporaryPassword`）、`PATCH /api/v1/users/{userId}/status`、`DELETE /api/v1/users/{userId}`（软删）、`POST /api/v1/users/{userId}/password-reset`（一次性临时密码）。**角色变更仍归 0580**（`PATCH …/role`），不在此面内。
- **唯一写者** `service/UserAdminService`：单事务固定序「实例锁（`instance_owner` 单例行）→ 目标 `users` 行锁 → 守卫 → 列写 → 双通道撤销 → durable 审计」；守卫优先级 `SELF_OPERATION_FORBIDDEN` → `INSTANCE_OWNER_PROTECTED` → `LAST_ADMIN`（后两者复用 0580 入口，但 last-admin **只统计可用 ADMIN**）；同状态请求为 200 空操作（不 bump、不审计）；拒绝审计 `user_admin_action_denied` 用独立事务落库，避免被守卫回滚吞掉。
- **双通道撤销**：access = `users.token_version` + claim `tv`（0580 交付，判定在 `AccessTokenAuthenticator`）；refresh = `users.session_version`（V86）+ claim `sv`（判定在 `AuthService.verifyRefresh`，四步：验签/未过期 → 行存在 → `status=ACTIVE` 且 `deleted_at` 为空 → `sv` 相等）。**禁用/软删/管理员重置密码**在同一事务同时 bump 两列（立即失效，不等 TTL）；**启用**不 bump（旧凭据不复活，需重新登录）；**角色变更只 bump `token_version`**，refresh 仍可用并按 DB 当前角色重签。非活跃账号在 access/refresh/login 三处一律走既有 401 语义，不产生 5xx、不泄露账号状态。
- **软删**：`deleted_at` + `status=DISABLED` 同写（V86 `ck_users_deleted_status` 兜底），v1 不可逆；`uq_users_email`/`uq_users_username` 保持原样（软删账号继续占用标识，决策 #7）。
- **注册策略**：`XIHE_AUTH_REGISTRATION_POLICY ∈ {open(默认), closed}`（bootstrap env，非 config 域），非法值启动 fail-fast；`closed` 时 `/auth/register` 在 0558 IP 限流之后、建号之前返回 403 `REGISTRATION_CLOSED`；localMode 不受影响。
- **D9 硬化**：`/internal/v1/config/effective/{domain}` 在 `userId` 与 `workspaceId` 都非空时校验成员关系，不满足 → 403 `WORKSPACE_FORBIDDEN`（复用既有码），置于 domain 校验之后、合并之前。契约见 [`spec/security/authentication.md`](../../../spec/security/authentication.md) §6 与 `docs/api/inventory.md`。

## 2. 会话级持久 SSE（PLAN-230）

- `SseEmitterManager` 按 `{sessionId, generation, emitter}` 存储，单会话单活；新连接替换旧连接（`chat_sse_replaced`），旧 `onCompletion` 用 `removeIfCurrent` 身份比对保护（误删记 `stale_cleanup_ignored`）。
- `POST /api/v1/chat` 先校验 `hasEmitter`（缺失 → `409 SSE_SUBSCRIPTION_REQUIRED`），再过 `SessionRunConcurrencyGate`：同会话非终态 run 计数已达 `agent-runtime.maxConcurrentRunsPerSession`（默认 2，PLAN-0645 M0/M1）才拒绝（`409 CHAT_IN_PROGRESS`）；cap 内并发提交各自 202。回滚口径：把该键设回 `1` 即恢复冻结的单飞行为，无需改代码。
- `done` 仅结束当前 `runId`，不关闭会话 SSE；`heartbeat` 15s 保活不进业务气泡。
- `requestId`/`runId` 由 `RequestIdFilter` 生成，经 `X-Request-Id`/`X-Chat-Run-Id` 显式透传至异步 `execAsync` 与 Agent（禁跨线程 MDC 继承）；`RequestIdFilter` 同时写 MDC `requestId` 并回写响应头。
- CP→Agent 聊天：`POST /internal/v1/agent/chat`（`stream:true`，SSE 回流）。

## 2.1 Workspace 级事件 SSE（PLAN-0350 首批）

- `GET /api/v1/workspaces/{workspaceId}/events` 按 `TenantContext` + Workspace membership 鉴权，不要求 Session 存在；订阅数按 Workspace 有界。
- Runtime 通过 `POST /internal/v1/runtime/workspaces/{workspaceId}/events` 上报归一化的相对路径/变更提示，CP 分配 Workspace-local `sequence` 并直接 fan-out。
- v1 不持久化 replay log；`Last-Event-ID` 发生 gap 时发送 `snapshot_required`，UI 通过既有 Workspace HTTP/MCP API 重建文件树和打开文件状态。
- 事件只携带摘要，不携带文件正文、完整目录树或宿主绝对路径；Workspace 删除提交后 CP 关闭相关订阅。

## 3. MCP 反代与工具命名空间

- `McpProxyController`：验 session-id HMAC 签名 + 提取 ws_id；`tools/list` 合并系统工具 + 各 STDIO server 工具 + 各 remote server 工具并建 tool→server 映射（5min TTL 缓存）+ sticky 别名落盘；`tools/call` 按三路（系统/stdio/remote）查表路由；命名 sticky（冲突仅新者加前缀，永不晋升）。
- **MCP caller 授权**：CP 按验证后的 Authentication 分流：User Bearer 仅调用 workspace UI 文件工具面，并经 membership + User grant；Agent internal service Bearer 的 `tools/call` 必须关联真实 application Session，并走 Agent principal grant path。`mcp-init` 不是 Session；Run/Invocation headers 不会把 User caller 转成 Agent。错误响应 requestId 沿用 RequestIdFilter，便于响应和审计关联；目标契约见 `spec/security/principal-workspace-scope.md`。
- **Agent durable caller gate（PLAN-0387 T3.2）**：在 grant、approval 与 Runtime dispatch 前，CP 核验 `sessionId/runId/toolCallId` 对应的 Session→ChatRun→`mcp_invocations(source=agent)`，匹配 owner、Workspace、Session、Run、Invocation 与 `toolName`，并要求 Run lease 与 invocation `active`。verdict 为空（无 invocation 行、Run 不存在）一律 fail-closed；UI-direct MCP 走独立路径。
- `ToolNameRewriter`（`read_file` ↔ `serverId__read_file`）：冲突时命名策略，已接线（PLAN-242 M2；全量前缀不取）。
- **CP-owned tool 的错误信封（PLAN-0649 M2）**：`spawn_agent`/`acquire_credential`/通用 CP 工具错误的 `result` 同时给两样东西——模型可见文本 `Tool error: <CODE>`（逐字节不变）与 `structuredContent.code`（仅码，无 `detail`/`status`，不把内部配额带上 wire），使 Agent 不必解析文本即可归类拒绝；码表权威在 CP（`DELEGATION_LIMIT_EXCEEDED`/`DELEGATION_POLICY_INVALID`/`SPAWN_ARGUMENTS_INVALID`/`SPAWN_EXECUTION_FAILED`/`ACQUIRE_EXECUTION_FAILED`/`TOOL_GRANT_DENIED`/`TOOL_CONTEXT_MISMATCH`，常量处 `cp/chat/ToolRefusalCodes.java`）。**码表是"已知码集合"，不是白名单**：形状合规的未知码必须原样显示，不得静默丢弃（否则新增码会变成"无原因失败"）。durable `tool.result` 侧只放行形状合规（`^[A-Z][A-Z0-9_]{0,63}$`）的 `refusalCode`，正文仍恒为占位符。
- **pre-dispatch 的三类拒绝都走工具结果信封（2026-11-04，0649 后续）**：`McpProxyController.handleToolsCall` 在派发**之前**有三道闸——上下文闸（`policy.hasCurrentAgentToolCall` 失败，审计 `agent_tool_call_context_rejected`）、授权闸（`policy.allowsByGrant` 失败，审计 `authorization_grant_denied`）、策略闸（`PolicyEffect.DENY`，审计 `deny`）。三者原先都返回裸 `403 FORBIDDEN` problem；MCP SDK 会把裸 HTTP 错误统一成 `Server returned an error response`，模型无法归类、卡片无 `refusalCode`（真栈实测：`spawn_agent` 六次失败全是这种形态）。现在统一返回信封（HTTP 200、`isError:true`、`content:"Tool error: <CODE>"` + `structuredContent.code`），但**码分两种**，因为给模型的可行动指引不同：
  - `TOOL_GRANT_DENIED`（授权闸 / 策略闸）= 没权限，**找管理员要授权**；
  - `TOOL_CONTEXT_MISMATCH`（上下文闸）= 调用上下文与 durable 的 Session/Run/Invocation/ToolCall 对不上，**重试无用，先修上下文**（stale run id、重放的 tool-call id、在别人的 run 里发起的调用）。
  durable 审计 action 与 SSE `tool_exec_denied` 事件名都保持原样（内部语义与 wire 码是两个关注点）。
- **会话权限快照不回溯（2026-11-04 补）**：`sessions.agent_permissions_snapshot` 在建会话时冻结（`SessionService.createAgentSession` → `resolveCapFor(principal, workspace)`），**之后改 workspace agent cap 只影响新会话**，既有会话继续按旧快照授权。真栈上"cap 已补 `exec`、委派仍 403"就是这条语义造成的（旧会话快照只有 `read`/`write`）。诊断第一步应比对**该会话**的快照而不是当前 cap。
- 服务间调用统一 `Authorization: Bearer`；自有 JSON 用 camelCase + RFC 9457 Problem Details（`code` + `requestId`）。

## 5. 会话 / 附件 / 文件 / 遥测

- **会话**：服务端 Session/Message 为 canonical source；`GET /api/v1/sessions/{sessionId}/messages?branchId=` 要求显式选择路径，只返回该 path 可见的历史（含附件）。
- **派生会话协作（PLAN-0408）**：child ChatRun terminal 与 parent Inbox 由 CP 同事务提交；提交后 CP 向 parent Session SSE 发 best-effort `derived_state_changed` 四键 hint。恢复读只使用 `GET /api/v1/sessions/{sessionId}/derived-state`；SSE 不是数据源。parent 删除只清 Inbox，不级联 child Session/ChatRun。生命周期契约见 [`spec/session/derived-collaboration-inbox.md`](../../../spec/session/derived-collaboration-inbox.md)，wire 见 OpenAPI 与 route inventory。
- **附件**：`File` 实体（`sessionId` + `messageId`，`workspaceId` nullable），物理路径 `{attachments-base-path}/{sessionId}/{fileId}`；`POST /api/v1/sessions/{sessionId}/attachments` 批量上传（白名单校验、500MB 上限）；`GET /api/v1/files/{fileId}` 取流（注意 `ChatAttachmentController` 返回的元数据 URL 缺 `/api/v1` 前缀，代码不一致待修，UI 依赖带前缀形式）；orphan 附件 24h 定时清理。
- **Fork 附件复制（PLAN-0409）**：child bytes 使用新 Session namespace 和新 File row；fork copy 与 direct/Session-wide physical delete 共用 per-File 行锁，cleanup 必须严格验证 child namespace 已不存在。持久 request/recovery 见 V46 与根 fork/action SPEC。
- **文件**：`WorkspaceFileController` 转发 Runtime REST（含二进制上传）；`GET /api/v1/workspaces/{workspaceId}/environment` 为只读诊断视图。
- **运行资源释放（PLAN-0391）**：`POST /api/v1/workspaces/{workspaceId}/runtime/release` 由任何有 access 的成员发起（平台 `ADMIN` 复用 environment admin 旁路；非成员 404），`Idempotency-Key` 必填（≤128），回收该 Workspace 的运行资源（watcher + 内存实例 + Job 进程树，**不删除容器**）。durable 操作落 `workspace_lifecycle_operations`（`status` accepted/running/completed/failed/interrupted）。存在 active Job 或在飞释放 → 409 `WORKSPACE_BUSY`；注销窗口 → 409 `WORKSPACE_DESTROYING`；Runtime 不可达 → 502 `RUNTIME_UNAVAILABLE`。`environment` 的 `runtime` 子对象增量 `activeJobCount`/`releaseOperationId`/`reason`（`USER_RELEASED`/`AUTO_EVICT`/`DESTROYED`/`CLEANUP_FAILED`/`RUNTIME_UNAVAILABLE`）。
- **遥测**：`TelemetryController` 收前端日志（`POST /api/v1/telemetry/logs` 需 JWT；`/anonymous` 限流），写 `telemetry.log`。
- **审计**：`AuditLogger` 记录 MCP 工具调用与策略决策，持久化到 `audit.log`（脱敏 encoder），内存保留最近 1000 条查询视图。

## 6c. source/env 状态与刷新（PLAN-0382，2026-10-01 冻结）

- **三态读取**：`RuntimeContextSourceClient.readAgents` 返回 `SourceRead(CONTENT|ABSENT|ERROR)`——`200 {found:false}`（PLAN-0427）= `ABSENT`；错误按 wire 表分流：传输/5xx → `unavailable`、4xx/畸形 200 → `failed`。重试 **≤1 次、立即、仅传输失败与 5xx**（CP 包规则禁 `Thread.sleep`，无退避 sleep）。
- **五值 `l1_status`**：`ok|missing|unavailable|failed|unknown`。`context.source_changed` 的 `status` 扩展承载 `missing/unavailable`，payload 同带 `l1_status`；projection 优先读 `l1_status`，legacy 事件按 `created/updated→ok、failed→failed` 派生。clear 族（failed/missing/unavailable）**同时清空 epoch `sources`**（BL-48，禁无标记回退）。

- **env 四值 `env_status`**：`ok|not_repository|unavailable|unknown`；Runtime 不可达保留 last-known-good 仅翻 `unavailable`；幂等双规则（六值集+状态相同不发事件，`observedAt` 不触发，状态翻转必发）；超时 connect 2s/read 10s、重试同上。legacy 无 `env_status` 键 → `unknown`（spec §5 执行表）。

## 7. 取消收敛与对账（PLAN-0317）

- **`POST /api/v1/chat/runs/{runId}/cancel` 由 CP 自主收敛**（不等 Agent 回音）：并行转发 Agent 与调用 Runtime 取消端点，终态只写入 `chat_runs`/`chat_run_history`，并在同一事务结算 Run waiting link、Inbox 与审批历史；取消不回写 MCP invocation 的执行事实。Run 下仍活跃的 invocation 按 MCP 执行域规则收口。

## 8b. Workspace 创建、目录选择与执行模式（PLAN-0379/0384）

- **删除（BL-174）**：`DELETE /api/v1/workspaces/{workspaceId}` 的授权是**能力判定**，不再是"仅 owner"：调用者是该工作区 `WS_OWNER`，或持 `cap:workspace:admin`（该工作区作用域、instance 作用域或 `cap:instance:admin`）。`WS_OWNER` 的原子集本就含 `workspace:admin`，故并集等价于"持该工作区管理能力"；**内容原子 `delete` 不构成删除工作区的凭据**（`WS_EDITOR` 可删文件，但删除工作区返回 `403 WORKSPACE_FORBIDDEN`）。自定义角色需要删工作区时授 `workspace:admin`。工作区不存在仍是 `404 WORKSPACE_NOT_FOUND`（不被 403 覆盖）。删除仍为软删（`deleted_at`），WorkspaceStorage 不删，Runtime 通知保持 after-commit best-effort；审计 `workspace_deleted` 追加 `actor` / `owner` / `crossOwner`（actor≠owner 时为 true），使跨归属的管理性删除与 owner 自助删除可区分。路由的角色门（`WorkspaceWriteGuard`）对该路由为 `SERVICE_CHECKED`：由 service 单点判，避免拦截器与 service 两套判决。
- **首用空白起步（PLAN-0614）**：`POST /api/v1/auth/{register,login,local-login,refresh}` **不再创建任何工作区**——只读该账号第一个活跃工作区（`AuthController.withFirstWorkspace`）；没有则 `AuthResponse.workspaceId=null`、`GET /api/v1/workspaces` 返回空数组，UI 停在选择面空态并引导创建第一个工作区。因此不存在"系统代用户创建的工作区"（I4），旧 BL-171（自动建的默认工作区用冻结 docker 后端）随之消失。首用步骤见 [DEV-033](DEV-033-first-run-gold-path.md)。
- **创建**：`POST /api/v1/workspaces` 接受 `storageMode`（`managed_import`/`direct_attach`）、`executionMode`、`hostPath`（仅 direct-attach）与 `Idempotency-Key`。**`storageMode` 必填、无默认值**（PLAN-0618 决策 #8：省略即 `400 INVALID_REQUEST` 并指向 `direct_attach`；`direct_attach` 必须带 `hostPath`/`executionMode`，"有默认值"本身就是假承诺）。v1 矩阵：`managed_import` 仅 `docker`（**已冻结**，见下条冻结门）；`direct_attach` 仅 `windows-mxc`/`windows-host` 且必带 `hostPath`；`profile`/`image` 仅 docker。direct-attach 在落库前先经 Runtime probe，probe 失败不落库。枚举值 `managed_import` **保留**（解冻后恢复使用）。

## 8e. 授权查表与分级查询（PLAN-0407）

- **授权 = grant lookup**：`GrantAuthorizationService` 按 gate order **HardGuard L0 → grant 查表 → approval** 评估；单主体权限集 = 该主体 `default|spawn|direct|template` grant 的 union，操作授权 = 驱动链上每个主体 permission set 的 intersection（atom `{actionClass, resource?}`，`resource` 缺省 `*`，无 `effect`、未列出即 deny；仅工具调用边界重算）。**grant deny 不进入 approval、不创建 pending approval**；词表外 actionClass、空集合与评估异常 fail-closed 拒绝。原「无规则默认 ASK」翻转为无权限集命中即拒不弹。

## 8e-2. 访问角色与绑定 API（PLAN-0610 W3-2a）

- **模型**：`roles` + `role_permissions`（只存原子名）+ `role_bindings`（role × subject × scope）。`scope_class`（`instance`/`both`）的 SSOT 在代码 `PermissionAtomCatalog`，`GET /api/v1/roles/catalog` 只是它的投影（18 原子 = 15 动作 + 3 能力）；API 不复制词表，新增原子自动出现在目录与写入校验里。

- **错误映射**：并发死锁/序列化失败（`40P01`/`40001`）在 API 边缘统一映射为 409 `CONCURRENT_MODIFICATION`（可重试），与锁等待超时（`55P03` → 503 `OPERATION_LOCK_TIMEOUT`）区分开——两者都是 `PessimisticLockingFailureException` 的子类，靠异常类型特异性保序。
- **作用域判定统一**：`AccessScopeResolver` 的成员校验新增 `AuthzContext.canWorkspaceAdmin` 回落（round-4 P2），使「实例管理员不是工作区成员」不再被成员门挡住；回落本身不授权，后续原子评估仍决定动作是否放行。
- **`users.role` 清零（PLAN-0610 W4a，V89 前置）**：账号实体不再映射该列，产品代码 0 读 0 写——建号（注册/管理员建号/`DataSeeder`）只写账号行，实例 tier 由 `GrantDefaultService.ensureUserDefault` 写 `USER` 绑定（本地单用户的 `SUPER_ADMIN` 仍由 `AuthController`/`DataSeeder` 的 bootstrap 路径绑定）；`GrantDefaultService.ensureInstanceTierBinding` 只补空缺、**不再按列改 tier**（tier 变更只走绑定 API 或 owner 交接）；`AgentTemplateService` 实例层模板 ACL 由 `actor.getRole()==ADMIN` 改为 `AuthzContext.isInstanceAdmin(actorId)`（round-3 P1-4），超管因 `SUPER_ADMIN` 种子含全部能力原子同样满足；`UserAdminService` 的「最后一个可用管理员」守卫改判**实例 `ADMIN`/`SUPER_ADMIN` 绑定的 ACTIVE 持有者计数**（`countActiveUsersWithInstanceRoles`）。副作用（已写进测试断言）：活跃调用者自身的管理员绑定必然计入，因此经该 API 已无法把实例降到 0 个可用管理员，`409 LAST_ADMIN` 保留为对陈旧能力/绕过写入的纵深防御。列本身与 `ck_users_role` 由 V89 删除。

## 9. Durable job 档案与续看（PLAN-0344）

- **档案（PLAN-0465 T1.2 迁 `workspace_jobs`）**：Job 状态是可变事实——`workspace_jobs` 行（`state` JSONB 保留 Job payload，`status`/`scope` 为同步查询列）按状态机前进 upsert（行锁串行化 + 唯一索引竞争重试一次；running → 终态一次性、终态不可回退/异终态覆盖丢弃）。canonical identity 是 domain `jobId`（=`workspace_jobs.id`）；`runtimeJobId` 为 Runtime backend handle。V56 已删除 `operation_item_id` anchor，pre-0465 `job_state` extension 不回填。每次状态前进同步 `workspace_job_history`（事件 `start/running/settle/cancel/orphaned/interrupted`）。字段与状态机冻结口径见 [PLAN-0344 job-freeze](../../../../plans/archive/20260918/PLAN-0344-XH-durable-job-continuation/evidence/job-freeze.md)。`scope` 取 `run/session/workspace`（缺省 `session`），是 Job 存活边界。
- **Start 与幂等（PLAN-0390 M2 / PLAN-0465 T1.2）**：`POST /api/v1/workspaces/{workspaceId}/jobs`（header `Idempotency-Key` 必填）在同一 REQUIRES_NEW 事务内创建 `workspace_jobs` 行与 start history，随后派发执行；幂等只由 domain 唯一索引负责（session 绑定 `(user_id, session_id, idempotency_key)`，session-less `(user_id, workspace_id, idempotency_key) WHERE session_id IS NULL`）；不再双写 legacy Ledger。Runtime start request 用 `jobId` 传域 ID；response 回显 `jobId` 并以 `runtimeJobId` 返回 backend handle。同 key 重放返回既有 Job（`200`，不产生第二个进程），同 key 但 input 不同 → `409 JOB_IDEMPOTENCY_CONFLICT`；缺 header → `400 IDEMPOTENCY_KEY_REQUIRED`；无 launcher → `501 JOB_BACKEND_LAUNCH_PENDING`；派发未确认 → `502 RUNTIME_UNAVAILABLE` 且档案落 `interrupted`。
- **Scope 收口**：run 进入终态收口该 `runId` 下 `scope=run` 的 active Job（`cancelReason=scope_run_end`）；session 硬删收口 `scope=session`（`scope_session_stop`）；Workspace 逻辑删除收口该 Workspace 全部 active Job（销毁路径落 `destroy_orphan`）。收口一律 best-effort 调 Runtime cancel，未确认时保留显式未确认态，不静默成功、不跨 scope 越界。
- **恢复**：`JobReconciliationService` 对账时若 Runtime `bootId`（`GET /internal/v1/runtime/diagnostics` 暴露）与档案 `runtimeBootId` 不一致，则该 Job 落 `interrupted`（`cancelReason=runtime_restart`）且**不自动重放**；SSE/HTTP 断线不改变 Job 状态。
- **三源回填**：① `McpProxyController` 在 start/get/cancel 工具成功后同步（best-effort，失败不影响派发）；② `JobReconciliationService` 周期（默认 5 分钟）只查档案内 running 的 jobId 走 Runtime `get_background_process`（不扫全容器），job 消失且非不可达 → `orphaned`；③ destroy 窗口内 Runtime `delete_workspace_handler` 在 destroying 标记后、容器 stop 前枚举存活 job 并随删除响应返回 `jobIds`，CP `markOrphanedForWorkspace` 落 orphaned（枚举失败 = fail-closed 全量落 orphaned）。
- **续看（PLAN-0465 T2.1）**：`GET /api/v1/workspaces/{workspaceId}/jobs/{jobId}/output`（Workspace access + `(jobId, workspaceId)` 双键归属；`jobId`=domain 身份）经 Runtime 内部路由读容器文件，并同时返回 `runtimeJobId`。分页按字节 `offset`（缺省 64KiB / 上限 1MiB），`nextOffset` 由 Runtime `utf8_safe_chunk` 保证恒为 UTF-8 rune 边界（CP 不做二次裁剪）；容器销毁 → 409 `JOB_OUTPUT_LOST`，终态但文件被 TTL 清理 → 409 `JOB_OUTPUT_EXPIRED`，Runtime 不可达 → 502。
- **计时**：运行时限按累计运行时间——空闲回收暂停前 `mark_jobs_paused` 打点、unpause 激活后折算 `paused_total_secs`，enforce 判定扣除暂停时长（消除「解冻即 timeout」误杀）。
- **唯一写者**：`workspace_jobs`（含 `state` 与 transition history）只由 CP 写；Runtime start request 接收域 `jobId` 并回显，后端 handle 独立返回为 `runtimeJobId`；status/output/cancel 使用 Runtime handle；Runtime 不写 CP 数据库。
- **单 Job 取消（PLAN-0366 / PLAN-0465 T2.1）**：canonical `POST /api/v1/workspaces/{workspaceId}/jobs/{jobId}/cancel`（Workspace access + `(jobId, workspaceId)` 双键）→ Runtime 内部路由 `jobs/cancel`（复用四阶段终止；`failed`=终止未确认）。已终态幂等 200 + 原状态 + `changed:false`；未确认 → 502 `JOB_CANCEL_UNCONFIRMED` 且档案不变；Runtime 404 → 档案落 `orphaned`（`cancelReason=job_missing`，与销毁/对账的 `destroy_orphan` 语义区分）；Runtime 不可达 → 502。取消 Job ≠ 取消 Run/对话终态；有效状态变化只写 `workspace_job_history`。

> **PLAN-0390 进度（2026-09-21）**：已落地 scope 字段（最终 schema version 1）、Workspace Job start（`Idempotency-Key` + V36 session-less 幂等）与 list 响应、Workspace access output/cancel、`interrupted` 对账。backend-neutral JobHandle/adapter、output cursor 完善、release/resume 和完整 scope termination 仍由 PLAN-0390 后续、0392–0395、0391 承接（接口冻结见 workspace 根 `plans/PLAN-0390-XH-execution-job-backends/spec/job-handle-contract.md`）。

## 13. 会话归属与显式工作区通道（PLAN-0608）

- **两条通道，一个判定**：`POST /api/v1/workspaces/{workspaceId}/sessions`（路径形式，优先）与 `X-Workspace-Id`（header，0559 解析）都汇入 `SessionCreationService` 的同一处 `SessionWorkspaceResolver`；两者同时给出且不一致返回 `400 WORKSPACE_CONTEXT_CONFLICT`，不允许「先到先得」的隐式选择。
- **B-narrow（只兜会话创建）**：两者都未给出且调用者活跃成员工作区 > 1 时返回 `409 WORKSPACE_CONTEXT_REQUIRED`；恰好 1 个（或 0 个）维持既有回退语义（回退到首个成员工作区 / 下游 401）。该收窄**只作用于会话创建**——`PolicyController`、`WorkspaceFileController`、`ChatAttachmentController` 仍使用既有回退值。
- **来源可判**：`TenantContext.workspaceSource` 记录本次解析来源（`header|claim|default`），与既有 `[TENANT] workspace_resolved … source=` DEBUG 日志同源，供排障与判据使用。
- **BL-182（主体缺失 = 403，不是 401）**：`ConfigController`×5 与 `PolicyRuleService` 的 `"User context is required"`、`WorkspaceJobController`×4 / `ScheduledTaskController`×7 / `McpSessionStatusController` 的 `"Authentication context is required"` 共 12 处守卫统一改为 **`403 FORBIDDEN`**（既有码，detail 文案保留）+ **warn 日志**（`event=context_guard_without_principal`，含 `detail`/`path`/`requestId`）。这些守卫在 `@PreAuthorize` 之后**正常不可达**，属不变式兜底（保险丝）：401 既不准确（主体其实已认证）又会被 UI 当会话过期强制登出；403 是权限语义且不触发登出，warn 让"不该发生"可查。入口收敛为 `ProblemDetailsHandler.missingPrincipal(...)` / `missingPrincipalException(...)` 两个方法。
- **BL-181（缺上下文 = 409，不是 401）**：**已认证但解析不到工作区上下文**（空白起步尚无工作区，或多工作区且未用 `X-Workspace-Id`/路径指定）在**所有** workspace 作用域端点统一返回 **`409 WORKSPACE_CONTEXT_REQUIRED`**（沿用会话创建既有码，`detail` = "Workspace context is required"），由 `ProblemDetailsHandler.workspaceContextRequired()` 与 `CpApiException.workspaceContextRequired()` 两个入口统一产出；原先 35 处 `401 AUTHORIZATION_REQUIRED` 已全部收敛。**`401 AUTHORIZATION_REQUIRED` 只保留给凭据缺失/失效**（无 token、签名/过期、`token_version`/`session_version` 失效）。理由：`/api/v1/**` 在 URL 层已要求已认证人类主体，401 既不准确又会触发 UI 的强制登出（`api.ts` 401 → 刷新 → 重放仍 401 → `forceLogout()`），空白起步用户点一下会话列表就被踢下线。
- **UI 口径（I6）**：登录不再把「登录响应里的工作区」写进 tab 上下文（那是回退值，不是用户选择）；无上下文时进入工作区选择页；创建会话走路径形式，`400/409` 时回到选择页而非只弹 toast。

## 14. 会话命令注册表与 `/export`（PLAN-0635 M3）

- **权威在服务端**（D35-02 裁定 A）：`GET /api/v1/sessions/{sessionId}/commands` 返回该会话**当前可用**命令；UI 只渲染，**不得自行过滤可用性**。响应纯标量 `{commands:[{name, source, available, reason}]}`，`source` 目前只有 `builtin`。
- **可用性复用既有 policy，不新造权限词**：`SessionCommandCatalog` 为每条命令声明一个**载具**——一个**既有 tool face 名**（如 `/export` → `read_file`），经 `PolicyEngine.evaluateVerdict(...)` 取 `effect`；`ToolFaceRegistry.builtinActionClasses()` 仍是唯一词表。**载具名不出 wire**（它是机制而非语义，暴露会让读者困惑"为什么 /export 是 read_file"）；排障靠结构化日志 `event=command_availability sessionId/command/policyTool/verdict`。
- **三档结果的呈现**：`ALLOW` ⇒ `available=true`；`ASK` ⇒ `available=false, reason=approval_required`（**不隐藏**——用户必须知道能力存在，UI 灰显 + 文案）；`DENY` ⇒ `reason=denied`；策略上下文读不出 ⇒ `reason=policy_unavailable`（fail-closed，不影响 run）。
- **`/compact` 不用 policy 门**，改**镜像其端点前置条件**：`POST /api/v1/sessions/{sessionId}/compact` 在活动 run 时返回 `409 BRANCH_LOCK` ⇒ 注册表对应 `reason=branch_locked`。原则：**UI 不得提供必然失败的命令**。该命令本身不新造端点（PLAN-294 decision #15 的既有入口）。
- **`/export` 是真产出**：`GET /api/v1/sessions/{sessionId}/export?branchId=` 由 `SessionExportService` 用既有消息读面（`MessageReadService.listVisibleMessages`）生成 Markdown，`text/markdown` + `Content-Disposition: attachment`；**不经 Agent、不调模型、不产生 run**（M1 桩的"发一句固定英文给模型"是反面）。有界：≤2000 条消息 / 单条 ≤20000 字符 / 整篇 ≤2000000 字符，截断在文档头以 `messagesTruncated`/`contentTruncated` 披露。
- **BL-295（2026-11-05，supersede BL-279 A1）**：**移除导出 413 预检**，导出语义收敛为"**有界导出**"而非"超限报错"。原因：BL-279 A1 的内存动机已被 **BL-279 B 流式**（`StreamingResponseBody` + 游标读 + 2M 字符 body）消除；而预检数的是 **session 全量行数**（不分 branch/可见性），实际会误挡"20k 会话里某分支只有 50 条可见"的合法导出。现在：对已授权 session/branch **恒 200**，唯一上限表达 = renderer `SessionExportService.MAX_MESSAGES=2000` + 文档头 `messagesTruncated`（及单条/整篇字符上限的 `contentTruncated`）；流式读取使内存与会话总条数解耦。被移除的 code/detail/日志：`413 EXPORT_TOO_LARGE`/`event=session_export_refused`。`MessageReadService.countSessionMessages` 仍保留给 `/messages` 的 `PAGINATION_REQUIRED` 天花板（PLAN-0670 M2b），与导出无关。
- **`/messages` 旧全量路径的硬天花板（PLAN-0670 M2b，2026-11-05）**：`limit`/`before` 都不带时保留旧契约（裸数组、不静默截断），但**兼容 ≠ 无界内存** —— 读取前先 `countBySessionId`，**> 2000** 条 ⇒ **`413 PAGINATION_REQUIRED`**（body 带 `messages`/`limit`，detail 指向 `limit`/`before` + `nextCursor`），**不读取任何消息行**；`≤ 2000` 仍走原全量路径（20k 夹具实测该路径单请求 ≈92 MB 堆、10 并发 873 MB，属 OOM 风险）。上限常量 `MessageReadService.MAX_FULL_READ_MESSAGES` **直接引用** `SessionExportService.MAX_MESSAGES`，两处守卫（导出/消息）共用同一个 2000 与同一套 `messages`/`limit` detail 结构，禁止出现第二个字面量。
- **堆水位诊断（PLAN-0670 M2b T2b.4）**：`SessionReadMemoryGuard` 在整段会话读面（`GET /messages` 旧全量路径、`/export`）估算响应字节约 2×内容字符数 + 每行 256B，超过阈值打一条 `event=session_read_memory_guard endpoint=… messages=… estBytes=… thresholdBytes=…`。**默认关闭**（`cp.read-memory-guard.enabled=false`，阈值 `cp.read-memory-guard.threshold-bytes` 默认 8 MiB），**日志不含任何消息内容/正文**。
- **v1 不含 skill 命令**：`/skill:<name>` 的候选必须来自 PLAN-0628 的 run 快照 listing（`skills_snapshot`）与按需正文（`skill_read`），两者在 0628 M2 前不落地（D35-07）；M3 只交付其形态设计。
- **C1 门**：两条路由均返回**纯标量 / 纯文本**，不经 Jackson-2 `JsonNode`（无 `JacksonNodeExit` 调用即无泄露面）。

## 15. 同源 UI 静伺服（`cp.ui.static-root`，PLAN-0632 D32-06 / M2-3）

- **默认关闭，语义只有一条开关**：`cp.ui.static-root`（env `XIHE_UI_STATIC_ROOT`）为空 ⇒ `UiStaticServingFilter` 是纯 pass-through，请求原样进原链路；dev/host 两条车道仍由 Vite dev server 代理 UI，**行为零变化**（`UiStaticServingFilterTest` 第 1 组断言钉住这一点）。指向一个目录（安装版由 launcher 设为 `<install>\ui`）才启用。
- **为什么是 filter 而不是资源处理器/兜底 Controller**：SPA 外壳必须在登录前可读（UI 自身渲染登录页），而 `SecurityConfig` 以 `anyRequest().authenticated()` 收尾；`@RequestMapping("/{*path}")` 这类兜底还会抢在 actuator 的 handler mapping 之前。filter 挂在安全链之前（`HIGHEST_PRECEDENCE + 100`），把改动**只**关在"配置了静态根"这一情形里。
- **不吞 API**：`/api`、`/internal`、`/actuator`、`/v3/api-docs`、`/swagger-ui`、`/swagger-ui.html`、`/error` 按**段边界**匹配后原样回原链路 ⇒ 401 仍 401、404 仍 404，绝不返回 `index.html`。（安装版实测：`GET /` → 200 且是 SPA；`GET /api/v1/workspaces` 无 token → **401**；`GET /api/v1/does-not-exist` 无 token → **401**——未认证先于路由解析，带 token 的未知路由才是 404。）
- **SPA fallback 只给"无扩展名"的路径**：`/workspaces/abc/sessions/def` → `index.html`；`/assets/missing.js` → **404**。若把缺失资源答成 index.html，浏览器会拿到 `text/html` 当 JS 执行，把"少打包一个文件"伪装成运行期语法错误。
- **路径穿越**：请求路径解码一次后拒绝 `\0` 与 `\`，任一段为 `..` 即 400，且结果必须仍在 canonical 静态根内（符号链接解析后再比对）——读不到安装目录之外。四类编码变体（`/../`、`%2e%2e`、`%2E%2E`、`%5c`）都有断言。
- **缓存策略**：`index.html` `no-store`（否则升级后仍引用旧 hash 资源名），其余静态资源 `public, max-age=31536000, immutable`；`X-Content-Type-Options: nosniff`。
- **配置了但目录不可用 = 保持 inert**（warn 日志），不做"半个启用"：启动器的 `ui` 阶段会以"CP 未返回 `/`"失败并给出提示，比 CP 对所有路由答 404 好排查。
