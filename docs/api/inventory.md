# Xihe API Inventory

This inventory is the implementation baseline for PLAN-222 + PLAN-230. It records the
current canonical routes after the targeted WorkspaceExecutionSpec migration and the PLAN-230 Chat SSE lifecycle freeze.

## Workspace context (PLAN-0559)

- Workspace-scoped user requests carry `X-Workspace-Id: <uuid>`. The header is authoritative; a missing header falls back to the legacy access-token claim, then the caller's default workspace.
- New access tokens are user-level (no `workspace_id` claim). `POST /api/v1/auth/refresh` accepts an optional `X-Workspace-Id` only to echo `workspaceId`; it never rebinds the token.
- Error contract: `400 INVALID_WORKSPACE_ID`, `403 WORKSPACE_FORBIDDEN` (non-member/deleted workspace or non-OWNER lifecycle), `403 WORKSPACE_READ_ONLY` (VIEWER write).
- Roles: OWNER (read/write/manage), EDITOR (read/write), VIEWER (read-only); legacy `ADMIN`/`MEMBER` rows project as EDITOR.
- `/api/v1/auth/**`, `/api/v1/health`, `/actuator/**`, `/internal/v1/**` do not use the header for tenant resolution.

## MCP Tool Surface

- Gateway-public built-ins are the 23 tools exposed by Runtime `#[tool_router]` and merged by CP `tools/list`; `apply_patch` is exposed to the Agent as an atomic multi-file mutation and is classified as `actionClass: write`, `shape: structured`, `REQUIRE_APPROVAL`.

## Contract Rules

- Public HTTP routes use `/api/v1`; service routes use `/internal/v1`.
- Service authentication is `Authorization: Bearer <token>` only.
- Xihe-owned JSON uses camelCase. MCP JSON-RPC fields and headers remain as
  defined by MCP `2026-07-28`.
- Cross-module execution correlation uses `X-Chat-Run-Id` + `X-Tool-Call-Id`,
  with `X-Mcp-Invocation-Id` for Runtime-reported late termination and `X-Job-Id`
  for optional Job-scoped routes. All correlation uses domain-owned IDs.
  ChatRun responses expose server-set `origin` (`user_submission` or `spawn`);
  public `POST /chat` cannot choose the origin.
- Spawn creation is a CP-owned MCP tool path: it validates the parent ChatRun and
  MCP invocation plus child Session provenance, uses the canonical toolCallId for
  idempotency, and skips only the browser SSE gate.
- Errors use `application/problem+json` with `type`, `title`, `status`,
  `code`, `detail`, and `requestId`.
- Login throttling (PLAN-0558): `POST /auth/login` and `POST /auth/register`
  return 429 `AUTH_RATE_LIMITED` with an integer `Retry-After` header and
  `Cache-Control: no-store`. Unknown accounts share the same response shape;
  counters are per CP process (single-instance v1).
- No query-string tokens, `X-Api-Token`, old path aliases, or field fallbacks.

## Policy Tool-Face Contract (PLAN-0328)

- `GET /api/v1/policy/tool-faces?scope=instance|workspace` returns a deterministic effective catalog sorted by `tool`.
- Built-in catalog entries use `scope: builtin`, `id: null`, and `ownerId: null`; persisted instance/workspace entries retain their UUID and owner identity and override entries for the same tool at lower precedence.
- `scope=builtin` is response metadata only and is not accepted by the write route. Role and tenant authorization remain server-side through `TenantContext`.
- Unknown third-party tools are absent from the catalog until their first approval request. Before explicit owner/admin classification, their policy face is `actionClass: unclassified`, `shape: opaque`, and the verdict is `ask` even under automatic modes; one-shot approval remains available while session/saved rule grants are rejected.

## Policy Rules Contract (PLAN-0328; rules CRUD retired by PLAN-0407 T2.8)

- `GET /api/v1/policy/domains` returns `actionClass`, `effectiveLayer` (`builtin` when no persisted layer configures the domain), `configuredLayers`, and `ruleCounts` (only layers holding at least one rule). This is the domain dictionary source; clients never infer the effective layer locally.
- The `/api/v1/policy/rules` routes (GET list / POST create / DELETE by id / GET conflicts) are **retired** by PLAN-0407 T2.8 together with rule adjudication: authorization is the grant lookup, the approval trigger is the `approval-policy.askActionClasses` list, and the permission-rules UI page retires with PLAN-0374 T3.4. Approval storage still writes rule rows internally (saved/reject tiers) but exposes no route.
- Remaining policy responses are camelCase with RFC 9457 Problem Details (`401`/`403`/`404`).

## Approval Grant Reuse Contract (PLAN-0328 T1.7)

- **Durable binding (V20/V21)**: `approval_requests` carries `policy_revision` (the durable monotonic `policy_revision.seq` counter, incremented for every policy/tool-face change, including deletion), `sandbox_generation` (`Workspace.generation` at decision time) and `reuse_scope` (`once|session|saved`; legacy NULL rows are treated as `once`, fail-closed). A plain `(session_id, tool, arguments_hash)` index backs the gate's idempotent lookup.
- **Consume checks (all fail-closed)**: a grant is consumed once and only while unexpired, with `rank(modeAtGrant) >= rank(currentMode)` (`manual > auto`; NULL mode ranks as `manual`), an unchanged durable `policy_revision`, and a matching `sandbox_generation`. Legacy rows without the V20 columns are rejected. The `approval_grant_consumed` audit record is emitted inside the consume transaction (R7).
- **Session tier = exact fingerprint**: a `session` decision records `{tool, arguments_hash, modeAtGrant, policyRevision, sandboxGeneration}` in memory (12h TTL, ≤64 entries/session, cleared on session delete) instead of a coarse L4 rule; the MCP gate dispatches the same invocation without a new pending approval and audits `grant_reused scope=session`. `saved`/`reject_always` keep writing persistent rules and now also record the new columns.
- **Gate idempotency + shape ceiling**: before creating a pending row the gate returns the live non-terminal row for the same `(sessionId, tool, arguments_hash)`. Allowed reuse tiers are shape-gated (structured → once/session/saved; structured+delete → once; interpreter → once/session; opaque/unclassified → once) and violations return `400 REUSE_NOT_ALLOWED_FOR_SHAPE`; unclassified tools keep their existing `409 TOOL_UNCLASSIFIED` path first.
- **409 APPROVAL_REQUIRED extension**: run-scoped ASK responses carry a JSON-RPC error frame (`error.code: -32003`, `error.message: APPROVAL_REQUIRED`) whose `error.data` holds `{status, code, approvalRequestId, tool, expiresAt, retryHeader, statusUrl?, policy?}`; MCP transports discard `application/problem+json` bodies, so the extension must travel in the JSON-RPC frame. Without a run context the gate keeps the legacy problem+json 409 (no extension; the Agent fails closed with no waiter).

## Chat SSE Contract (PLAN-230)

- **Persistence**: `GET /api/v1/events?sessionId=` is a session-scoped long-lived SSE. `done` terminates a *run*, not the SSE. Only client disconnect, session deletion, or explicit server termination closes it. Heartbeat `event: heartbeat` every 15s; never enters UI `MessagePart`.
- **Identity**: One active emitter per `sessionId` (v1). `SseEmitterManager` stores `{sessionId, generation, emitter}` and uses `compareAndRemove`; new connection replaces old (`chat_sse_replaced`) and old `onCompletion`/`onTimeout`/`onError` that no longer own the entry are logged as `chat_sse_stale_cleanup_ignored`.
- **Gate**: `POST /api/v1/chat` checks `hasEmitter(sessionId)` *before* persisting the user message. On miss: `409 SSE_SUBSCRIPTION_REQUIRED`; on concurrent run: `409 CHAT_IN_PROGRESS`; Agent circuit open returns `503 AGENT_CIRCUIT_OPEN`.
- **Events per run**: `connected` (SSE open) → optional `status`/`thinking` → optional `tool_call`/`tool_result` → `token` (≥1) → `done` (exactly one; `error` + `done(error)` on failure). Real MiMo long replies produce ≥2 `token` events; `on_chat_model_end` fallback fires only when no `on_chat_model_stream` was emitted (`LangGraphEventAdapter` per `run_id`).
- **Diagnostics (PLAN-0342)**: a failed, parseable command result may add an optional `diagnostics` bundle (`{items, total, confidence}`; `items` is the Top-N slice of `total`) to the `tool_result` data — copied from the Agent tool-message artifact channel and relayed unchanged by CP; the model-visible `<diagnostics>` block stays inside the untrusted envelope.
- **Transport telemetry (PLAN-0508)**: bounded provider-attempt telemetry rides the session channel as `transport_progress` (`{requestId,runId,attemptId,seq,stage,startedAt,elapsedMs}`; stages `attempt_started|first_chunk|streaming|attempt_finished`, at most four per attempt, never per chunk) and `transport_attempt` (`{requestId,runId,attemptId,seq,startedAt,endedAt,durationMs,outcome,errorCode,firstChunkMs,chunkCount,uploadBytes,downloadBytes}`; outcome `success|error|timeout|aborted`, exactly once). CP persists the durable `chat_run_transport_attempts` row before relaying (`GET /api/v1/chat/runs/{runId}/attempts` is the authoritative read surface; ordering vs other events is not guaranteed). Elapsed/duration come from the Agent's single-process monotonic clock only — `startedAt/endedAt` are display facts and never subtracted cross-process; running/partial rows without summary keep `durationMs` null. Wire bytes are fixed null in v1.
- **Approval**: `approval_request` is persisted by CP before dispatch to the UI and its live/replay envelope contains canonical `requestId/runId/sessionId/workspaceId/tool/action/details/expiresAt/replayed` (`requestId` is a UUID), with optional legacy-preserved `argumentsHash/state`, the durable creation `origin` (`cp_gate` for CP-gate rows, `agent_relay` for model-initiated `request_approval`; null for pre-V25 rows), plus an optional safe `policy` summary (`effect/sourceLayer/matchedRule/reason/mode/actionClass/shape/reused`, with `modeAtGrant` when emitted); it never includes raw tool arguments. Browser decisions use `POST /api/v1/chat/approvals/{requestId}/decision`, while CP alone calls Agent `/internal/v1/agent/approval/respond`. The Agent `/internal/v1/agent/approval/{requestId}` status is a separate raw coordinator response and does not carry the CP policy summary or replay/state fields. Reconnect replays live approval/retry requests for the same authorized session only; `dispatching` is in-flight and not actionable in the UI. Post-gate (T1.7/T1.9): a run-scoped ASK without a valid consume or session grant creates/reuses the durable pending row and answers `409` with a JSON-RPC error frame whose `error.data` carries `approvalRequestId/tool/expiresAt/retryHeader/statusUrl/policy`; without a run context the gate keeps the legacy problem+json 409 without extension.
- **Observability**: CP logs `chat_sse_registered` / `replaced` / `stale_cleanup_ignored` / `client_closed` / `send_failed` with `sessionId` + `connectionGeneration`; `chat_run_started` / `forwarded` / `finished` / `failed` with `requestId` + `runId`; `chat_stream_event_received` / `relay_finished` with `eventIndex` + `tokenCount` (never token content). `requestId` from `RequestIdFilter` is explicitly propagated to `execAsync` via `X-Request-Id`/`X-Chat-Run-Id` (not thread-local).
- **UI**: `chatTransport` enforces single flight per session (`connectionGeneration` + `intentionalStops`), `fetch-event-source` retry is *solely* in transport (`onerror` returns explicit backoff 250ms→5s, `onclose` schedules at most one reconnect; no second retry loop). `useSSE.ensureConnected()` + one-shot `409` recovery, `SSEStream` replaces streaming parts on every `token` (`replaceStreamingParts`).

## ChatRun Contract (PLAN-247)

- Public CP `POST /api/v1/chat` creates only `origin=user_submission`, after readiness, SSE subscription, authorization, and single-flight gates pass. User submission idempotency is `(userId, sessionId, Idempotency-Key)` with request-hash comparison; any client-supplied `origin` is ignored and never controls persistence.
- CP-owned `spawn_agent` accepts only an MCP invocation belonging to the parent ChatRun, validates the parent and child Session provenance, and bypasses only the browser SSE subscription gate. The canonical toolCallId is the child ChatRun idempotency key; V39 enforces `(user_id, idempotency_key) WHERE origin='spawn'`. Same toolCallId/hash replays the existing run; a different hash returns `409 IDEMPOTENCY_KEY_CONFLICT`.
- PLAN-0630 M1: the delegation budget gate sits **after** the same-`toolCallId` idempotency replay and **before** the one-shot approval is consumed. Do not move it earlier (a retry would be refused because its own child fills the last slot) or later (a refusal would burn the user's approval).
- Spawn accepts attachment IDs only; CP reconstructs summary/hash from child-owned File rows. Parent Session files and caller-supplied attachment JSON are not implicitly shared.
- Public `POST /api/v1/chat` cannot replay or return a spawn run, even if the caller reuses the same key; it returns `409 IDEMPOTENCY_KEY_CONFLICT`. Agent production caller is the CP-owned logical MCP tool `spawn_agent` after the existing grant/approval gate; the direct internal route remains a CP service surface, not an Agent caller (PLAN-0407 T2.10).
- PLAN-0510 continuation uses a new child ChatRun with `origin=user_submission` plus private continuation provenance; `resume_pending` appends no message and `append_user_turn` persists exactly one. The public response contains only child `runId` and accepted `mode`; CP sends checkpoint coordinates and the bounded `completedToolCallIds` projection only in its authenticated internal Agent request, where Agent preflight must prove safe checkpoint ToolMessages before resuming.
- Terminal outcomes are `success`, `error`, `partial`, and `ambiguous`. A provider disconnect with uncertain execution is `ambiguous` and must not be automatically retried. Manual retry uses a new key.
- `/api/v1/exec` is intentionally absent; callers use `/api/v1/chat`.

## Checkpoint Slice Contract (PLAN-0338 + PLAN-0339)

- **Runtime routes (internal, CP is the caller)**: `POST /internal/v1/runtime/workspaces/{workspaceId}/checkpoints/capture` (`{runId, actor, callId, abnormal}` → `{runId, noChange, sliceRef, commit, capturedAt, state, changedFiles, opaqueNestedRepos, predecessor}`), `POST .../checkpoints/gc` (slice retention counts), `POST .../checkpoints/cleanup` (`{removed}`; idempotent, `409 CHECKPOINT_BUSY` while capture/restore is active), `POST .../checkpoints/revert/preview` (`{sliceRef}` → `{sliceRef, counts:{restore,delete,typeConflict}, entries, truncated}`), `POST .../checkpoints/revert` (`{sliceRef, acknowledgeTypeChanges}` → `{sliceRef, counts:{restored,deleted,failed}, entries, durationMs, suspects}`), `GET .../checkpoints/blob?sliceRef=&path=` (plain text ≤ 1 MiB), and `GET /internal/v1/runtime/workspaces/{workspaceId}/git-status` (`{isRepository, entries}`; non-Git workspaces answer `false`). All service errors use RFC 9457 Problem Details.
- **CP checkpoint 切片记录 (`run_checkpoints`, rebuilt by PLAN-0339 V27)**: workspace slice rows, with no Run-scoped compatibility row. States are `captured | abnormal-captured | degraded | expired`; expired rows are not returned by the public list. `unrollableReason` is `UNAVAILABLE`, `INVALID_REQUEST`, `GIT_UNAVAILABLE`, `GIT_TOO_OLD`, `GIT_FAILED`, `WORKSPACE_UNKNOWN`, `NESTED_REPO_LIMIT`, or null; `EXPIRED`/`TOO_LARGE`/`MISSING`/`DEGRADED` are gate-only and are not capture-durable values. PLAN-0502 seam A adds a durable `root_id` column (V76) attributing each slice to a root — it equals the workspace identity in the single-root model and is **not** exposed in the API.
- **Revert bookkeeping**: `revert` contains `state` (`none | rolled_back | partial | failed`), `at`, `counts`, `ref` (the restored slice ref), and `attemptCount`, persisted directly on the `run_checkpoints` row. The summary is bounded and never contains raw arguments or file content.
- **Public workspace routes**: `GET /api/v1/workspaces/{workspaceId}/checkpoints` returns the direct JSON slice array; `POST .../checkpoints/revert/preview` accepts `{sliceRef}`; `POST .../checkpoints/revert` accepts `{sliceRef, acknowledgeTypeChanges}` (both refuse with `409 RUN_ACTIVE` while a ChatRun is active in the workspace, checked before slice resolution); both OK responses carry `descendantsAffected: [{sessionId, overlappingPaths}]` (PLAN-0640 T1: spawn-descendant sessions whose post-target work overlaps the rollback paths, BFS over the durable `sessions.spawned_from_session_id` edge — informational only, never blocks the restore); `GET .../checkpoints/blob?sliceRef=&path=` reads a slice file; `POST .../checkpoints/cleanup` requires `{acknowledge:true}` and clears CP rows only after Runtime cleanup succeeds. All are owned by `requireAccessibleWorkspace` (404 `WORKSPACE_NOT_FOUND`), and the Agent has no restore route.
- **Retained workspace routes**: `GET /api/v1/workspaces/{workspaceId}/git-status` remains the user-repository side of the dual diff; `GET .../checkpoints/retention` keeps the fixed newest-50/30-day policy; `POST .../checkpoints/gc` returns Runtime sweep counts.
- **Trigger and safety**: capture occurs once at Run termination, during abnormal recovery, or for C0 materialization; unchanged trees do not create a slice. Restore previews list all paths that will be restored or deleted, mark `truncated` when bounded, require explicit type-change acknowledgement, and report concurrent-write `suspects`. Capture/restore use short locks; a restore does not block concurrent writes, so the risk remains visible in the preview/result.

## Tool Timeout Budget (PLAN-0308 M1)

- **per-call request**: `POST /api/v1/chat` accepts an optional `toolTimeouts` object (`{toolName: seconds}`) — the highest-priority input to the tool budget. Values are positive integer seconds, max 600 (code constant); invalid or oversized values return `400 INVALID_REQUEST` naming the offending key (never silently clamped). The map participates in the idempotency request hash, so replaying a key with different timeouts is `409 IDEMPOTENCY_KEY_CONFLICT`, not a silent reuse.
- **CP → Agent delivery**: CP is the only timeout calculator; the run payload carries `toolWaits` (final per-tool Agent wait = budget + 4s), `toolWaitOrigins` (`per-call | config`), `systemToolWait` (single value covering all system tools), raw `toolTimeouts`, and `budgetCoverage` (`partial` when the tool→server cache was cold). The Agent only consumes these values (three judgments, no arithmetic).
- **CP → Runtime delivery**: `X-Xihe-Tool-Timeout-S` (Runtime budget) and `X-Xihe-Tool-Timeout-Origin` are set by CP alone; upstream same-name headers are stripped at ingress, and a validated inbound per-call header is stripped before forwarding. The same headers ride both the system/stdio and remote forward paths.
- **Agent → CP (per-call carrier)**: when the run payload has a per-call entry for the tool being called, the Agent attaches it as the inbound header `X-Xihe-Tool-Timeout-Per-Call`; CP validates it (positive integer ≤ 600, else `400`) and forwards with `valueOrigin=per-call`, which overrides each hop's own ENV.

## Agent Run Budget (PLAN-0492)

- **Config surface**: the `agent-runtime` domain carries `runMaxTurns` (one turn = one completed LLM call), `runMaxElapsedSeconds` (cumulative wall clock, paused during approval/human waits), and `runMaxTokens`, all writable at user/workspace scope; `runMaxTurnsCeiling` / `runMaxElapsedSecondsCeiling` / `runMaxTokensCeiling` are instance-only (`0` = no clamp) and the effective value is `ceiling > 0 ? min(value, ceiling) : value` (clamps log `run_budget_clamp`). Any value `0` disables that dimension (counted and reported, never stopping the run). Code defaults: turns 25/100, elapsed 600/3600, tokens 38303/51070 (calibrated 2026-10-13 from real-provider runs, p95=25535 over 15 runs; PLAN-0492 `evidence/m0-token-calibration.md`).
- **Agent → CP (stream)**: an exhausted run emits one structured `error` event with `code=RUN_BUDGET_EXHAUSTED`, `dimension` (`turns | elapsed | tokens`), `retryable=false` and `outcome`; the Agent SSE mapping must carry `dimension` through (pinned by `tests/unit/test_chat_budget_error_sse.py`).
- **CP mapping**: the relay records the dimension in the durable terminal write (`errorDetail=budgetDimension=<dim>` and the run-history payload) and converges the run to `failed` (`partial` when assistant content already streamed); `terminalOutcome` stays the existing enum value `error`.
- **UI**: the assistant message renders the localized reason plus the resume hint; takeover is the ordinary send / Follow-up Queue path and never resumes the old run's graph state.
- **Delegation budget (PLAN-0630 M1)**: `agent_principals.delegation_policy` (V100, JSONB NULL, service-validated — no DB CHECK, same as `context_policy` / `hooks`) = `{maxCount >= 1, maxDepth >= 1}`; NULL means code defaults `8 / 3`. Instance ceilings `delegationMaxCountCeiling` / `delegationMaxDepthCeiling` (`agent-runtime`, instance-only, `0` = no clamp; effective value = `min(policy, ceiling)`). Judged in CP, pre-persist, inside the parent Session+Run row locks: **budget root** = walk up the spawn edges, stop at the first non-spawn session (a fork counts as a root — it is a new authority root, so the walk must not test `kind IS NULL`); **depth** = root 0, +1 per spawn edge, refused when `depth > maxDepth`; **count** = spawn sessions in the root tree that have a non-terminal run, refused when `used >= maxCount` (a child's terminal run releases its slot). Only the ROOT subject's policy is read — a sub-agent's own limits are inert as a subagent. Refusals: `409 DELEGATION_LIMIT_EXCEEDED` (depth/count) and `409 DELEGATION_POLICY_INVALID` (unreadable stored policy or broken tree, fail-closed); one durable `agent_spawn_refused` audit row written **outside** the rolled-back transaction, no Session/run/participant row and no approval consumption. The delegation edge needs no new columns: it stays `sessions.{kind, spawned_from_session_id, spawned_from_run_id}` + `chat_runs.{waiting_on_run_id, waiting_tool_call_id}`.
- **Wake-chain depth (PLAN-0630 M1)**: the same `agent-runtime` domain carries `wakeChainMaxDepth` (default `3`, **instance-only**, `1`–`10`). It bounds the 0624 wake chain: user message = depth 0, the first woken agent = 1, and the next link beyond the limit is refused with a visible `wake_dispatch{outcome=chain_refused, reason=depth_exceeded}` event (no run is created). The same domain also carries the delegation ceilings `delegationMaxCountCeiling` / `delegationMaxDepthCeiling` (instance-only, `0` = no clamp). It is resolved without user/workspace context, which is why it is instance-only — a user/workspace value would be writable but never read.
- **Wake edge (PLAN-0630 M2 T1.7, V105)**: `chat_runs.parent_run_id` UUID NULL — the durable wake edge ("which run's output woke this run"), the only new column of PLAN-0630. No FK (same ruling as the V37/V52 carriers: no cascade through this edge), partial index `idx_chat_runs_parent_run`, and `ck_chat_runs_parent_run_not_self` fences the self-reference; longer cycles are path-scoped in CP and keyed on `sessions.agent_principal_id` (same principal twice on the path ⇒ refuse), not in the DB. Historical rows keep NULL = root (no backfill). Spawn runs do NOT write this column — their parent edge is already `waiting_on_run_id`, and writing one fact into two columns would be a second source of truth. Walk semantics (PLAN-0630 M2/M3): chain depth is **never persisted** — each derivation walks the edge in place (≤ 10 hops, D30-03/D30-05); a missing ancestor row (session physically deleted) refuses the derivation fail-closed with `ancestor_missing` instead of treating the orphan as a new root (D30-08).
- **Route surface**: no new HTTP route; the existing `POST /api/v1/chat` and session SSE carry the behavior. Error code enum in `docs/api/openapi.yaml` is not closed (free-form string), so no schema change is required.
